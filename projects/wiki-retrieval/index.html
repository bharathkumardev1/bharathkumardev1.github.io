What each stage of a search stack buys

I wanted to know which stages of a passage search stack earn their cost, so I built one on a corpus large enough that approximate search is a real trade-off and measured every stage against the one before it. Some stages paid. Mined hard negatives didn't, my first answer judge was no better than a constant, and the refusal gate turned out far stricter inside the agent than on paper.

Corpus
2,681,468 passages and 3,452 queries from BEIR Natural Questions, plus a 104,201-passage dev slice for iteration
Headline
nDCG@10 0.402 for the LoRA bi-encoder on the full corpus, against 0.290 for my BM25 with Lucene defaults
Fine-tuning
+0.014 nDCG@10 [+0.007, +0.021] over the untuned encoder, paired, permutation p 0.00012. Small, and clearly not noise
Reranker
+0.094 on the dev slice (0.783 to 0.877) at about 800 ms per query on 2 vCPU. Not run on the full corpus

The stack

Wikipedia dump (.bz2) -> Go ingester: parse, clean, split, deterministic ids
BEIR NQ corpus + queries + qrels -> LoRA on MiniLM (InfoNCE) -> fp16 embeddings

query -> BM25 (numpy, Lucene idf) --------------------------\
      -> encoder -> IVF-PQ candidates -> exact re-score ------> RRF -> [INT8 cross-encoder] -> results
                                                         semantic cache, keyed by index version
  • BM25 is my own numpy implementation, because bm25s ran out of memory at about 120 million postings. With Lucene defaults it lands just below the published BEIR figures, so I call it the same ballpark and claim no reproduction.
  • The encoder is msmarco-MiniLM-L6-cos-v5 with a LoRA adapter (rank 16, 8,000 training pairs, one epoch). I ruled out the better-scoring all-MiniLM-L6-v2 because Natural Questions is in its training data, which would contaminate this evaluation. I measured it once and kept the file to show the gap.
  • FAISS IVF-PQ picks 1,000 dense candidates and exact float32 vectors re-score them. BM25 and dense results are fused by reciprocal rank.
  • An INT8 ONNX cross-encoder can rerank the head. A FastAPI service adds a semantic cache keyed by index version, and Prometheus metrics.
  • A LangGraph agent drafts a cited answer, verifies each cited sentence and refuses when verification fails. It runs from scripts only; the API doesn't call it.

Every number on this page comes from a file in results/, and docs/readme_tables.py --check fails when the README drifts from those files. Each design choice has an ADR in docs/adr/ with the alternatives I considered.

Full corpus

This is the corpus comparable to published BEIR numbers. I encoded it on a Kaggle T4 and searched it exactly, dense only.

Paired over the same 3,452 queries, LoRA beats the untuned encoder by +0.0137 nDCG@10 [+0.0066, +0.0208], permutation p 0.00012, with 783 queries better, 699 worse and 1,970 tied. Recall@100 gains more, +0.043. The tuned arm was picked from three trained on the same test queries, so that p-value isn't adjusted for the choice. Tuned BM25 (k1 0.9, b 0.4) scores 0.309 on the 2,952 queries not used for tuning, against 0.295 for the defaults on those same queries.

What compression costs

Full corpus, one query at a time, 4-CPU Kaggle host.
Searchp50Held in memory
Exact float32, flat inner product321 ms4.12 GB of vectors
IVF-PQ 48 B per vector, nprobe 642.63 ms129 MB of codes
IVF-PQ 96 B per vector, nprobe 644.61 ms257 MB of codes

Compressed codes alone are about 70 times faster than exact search and give up 0.031 nDCG@10 at 96 bytes and 0.069 at 48. The exact re-score wins most of that back, but I only measured it on the dev slice, and it needs the float vectors in memory, so a served process holds the full matrix next to the codes. I report the speed-up and that memory cost together.

The serving stack on the dev slice

The dev slice is every judged passage plus 100,000 random distractors. It's much easier than the full corpus (tuned BM25 scores 0.68 there against 0.309), so these numbers are never compared with the table above.

The compressed path costs 0.0025 nDCG@10 against exact hybrid search, and the paired interval excludes zero, so I report it as a cost, not a tie. The reranker is the biggest gain in the stack and also the slowest stage: 794 ms p50 over all 3,452 queries on 2 vCPU, with a long tail (p95 1,848 ms) that I can't separate from host noise. BM25, dense search and fusion together take about 2 ms. Reranking the top 10 instead of 20 scores 0.859 against 0.877, which is the knob I'd turn first without a GPU.

Mined negatives lost

Hard negatives are the standard advice for contrastive fine-tuning. Here they lost.

Dev slice, dense only, paired over queries.
ComparisonnDCG@10 differencehit@10 difference
LoRA, random negatives, minus untuned+0.0399 [+0.0328, +0.0468]+0.0371
BM25-mined negatives, minus random-0.0035 [-0.0066, -0.0005]-0.0035
Dense-mined negatives, minus random-0.0023 [-0.0056, +0.0010]-0.0067 [-0.0116, -0.0020]

I kept random in-batch negatives. Training loss averaged 0.063 with random negatives, 0.128 with BM25-mined and 0.180 with dense-mined. I didn't test why the mined ones didn't help. Too few pairs, unlabelled positives among the mined passages, the sampling window and a single seed are all possible.

Cited answers and refusal

My first answer check was lexical overlap between a cited sentence and its passage. I labelled 300 answers by hand to test it. It called 194 of the 200 system answers supported, so its kappa against my labels, -0.006, is what a constant predictor scores. A cross-encoder scoring the question against the cited passage separated much better (AUC 0.87 for not supported against the rest), so I rebuilt that stage as a refusal gate.

Gate on my labelled sheet, cross-fitted over 40 random splits.
MeasureValue
Labels: supported / partial / not supported48 / 76 / 76
Not-supported answers refused75.3%
Acceptable answers wrongly refused20.8%

Wiring it into the agent showed a second problem. On 300 sampled questions the agent with the lexical check answers 251. With the gate it answers 58, and the share whose cited passage I'd labelled relevant goes from 69.7% to 94.8%. Most of that jump comes from answering 193 fewer questions, not from better answers. The sheet scored one cited passage per answer, while the agent requires every claim to clear the threshold, which explains a stricter result. I never counted claims per answer, and the threshold was fitted on the same questions, so that run is in-sample. A gate whose sheet says 21% false refusals and whose agent refuses 80% needs a per-claim threshold before anyone leans on it.

The gate scores relevance, so a wrong sentence from a relevant passage gets through. The drafter copies sentences from the passages. I tried Qwen2.5-0.5B as a drafter on 5 questions and it refused all 5, so no real language-model drafter has been evaluated. 400 prompt-injection trials changed no answers.

Errors I found in my own work

  • An evaluation script scored the same ranking twice for one depth setting, and the reranker came out at nDCG@10 0.0003. That value couldn't be right. The fix is an assertion that every query has exactly one ranking, so a quieter version of the bug now fails loudly.
  • I first wrote in an ADR that the dev slice came from the Simple English dump. It's a slice of BEIR NQ, and the ADR now says so.
  • The full-corpus adapter gain first had no paired test, because the run didn't save per-query scores. The paired run does, and the shipped file holds the nDCG@10 arrays.

Limits

  • The re-score and the reranker are measured on the dev slice only, and the full-corpus hybrid has no number at all.
  • The fine-tuning gain on the full corpus is small, 0.014 nDCG@10.
  • Labels come from one person, and that person is me.
  • Inference is CPU-only, so a 20-candidate rerank costs about 800 ms.
  • Service load numbers are synthetic: a 2 vCPU container, one request at a time, with the load generator on the same CPUs. Retrieval alone answers at p50 16.5 to 18.4 ms; with the reranker, about 900 ms.
  • The Kubernetes manifests have never been applied; Terraform ran against LocalStack only.
  • Five test queries share their text with training questions, and I haven't rerun the evaluation without them.

What I'd run next: the re-score and the reranker on the full corpus, since both claims rest on the slice; then a per-claim gate threshold and a second annotator; then a real language model as the drafter, with the gate measured against it.

Run it yourself

python -m venv .venv
.venv/bin/pip install torch --index-url https://download.pytorch.org/whl/cpu
.venv/bin/pip install -e '.[serve,agent,dev]'
.venv/bin/python -m pytest -q    # 82 tests, no data needed

make dev-data       # BEIR NQ (about 765 MB), builds and encodes the dev slice
make serve-untuned  # http://localhost:8000, POST /v1/search

Encoding the dev slice takes about half an hour on 2 vCPU. The full-corpus numbers need a GPU; the three Kaggle notebooks' source is in kaggle/. BEIR NQ's licence is contradictory, so I treat it as non-commercial and ship scripts, not data.
