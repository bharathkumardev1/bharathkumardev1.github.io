Forecasting taxi demand, and where the model loses

For each of NYC's 262 taxi zones, forecast pickups in the 15-minute slot that starts an hour after the last slot seen. Fitting a model is the easy part. What I wanted to know, with leakage ruled out and against baselines I hadn't weakened, was where the model is better and where it isn't, and what the service does when the model is down.

Data
Yellow-taxi trips, January to June 2023, as a dense zone-by-slot panel with explicit zeros
Test
Rolling-origin backtest over three June weeks, each trained only on earlier data with a one-horizon gap
Result
WAPE 0.2415 against 0.3104 for the best of three baselines, 22% lower. It loses in the two quietest zone quartiles
Serving
With the model killed, 40 of 40 gateway requests came back from the fallback; after restart, 20 of 20 from the model

How it's built

TLC parquet -> schema check -> dense zone x 15-min panel (explicit zeros)
            -> origin-relative features -> rolling-origin backtest / LightGBM (Poisson) -> ONNX

client -> Spring Boot gateway (Java 17, resilience4j)
            |  150 ms timeout, circuit breaker (20 calls, 50% failures, 10 s open)
            |-> FastAPI service: features from a history snapshot -> ONNX -> /v1/forecast, /metrics
            '-> on timeout or open breaker: stored per-zone value

The panel holds explicit zeros because a zone with no pickups in a quarter hour is a real observation, and lag features over a sparse panel would silently read the wrong row. Features are computed relative to each forecast origin: seven lags, three rolling means, the same slot a day and a week earlier, and calendar fields. A test checks that changing any value after the origin never changes the features, and that the online feature path matches the batch path.

The target is the slot that starts 60 minutes after the origin, so observed data ends 45 minutes before it starts. The baselines use the same timing, and all four forecasts are scored on the same rows.

In the two quietest quartiles, 0.28% of trips, the model is worse than every baseline. These quartiles rank zones by their trips in the test weeks, which sorts by the outcome. Ranking by trips before the first test week instead moves 26 of 262 zones and leaves the finding in place.

I tried routing quiet zones to the seasonal baseline, with the threshold chosen on a separate validation week. Pooled WAPE moved from 0.2412 to 0.2406. That 0.0006 is the size of the seed differences I saw in single folds (up to 0.00073), so I report the weakness and leave the fix open. What I'd want is a shrinkage model for sparse series, and I haven't built it.

Calendar and same-slot features carry the model. The lags cost 0.0007, more than the seed spread in the mean but about the size of single-fold seed differences, so I wouldn't call them useful or useless. If serving cost mattered, they'd go first. Each ablated run used one seed.

I also trained separate zone, borough and city models and reconciled them so children sum to parents. Shrunk MinT lowered zone WAPE from 0.2412 to 0.2384 and raised city WAPE from 0.0593 to 0.0600, so I read it as coherence at no measurable cost. The more useful finding: summing zone forecasts is plainly worse than modelling the city directly, 0.0659 against 0.0593.

Serving and the fallback

The service runs the model as ONNX. The converter drops LightGBM's categorical splits and inputs become float32, so I checked parity on the held-out week: WAPE 0.25483 for LightGBM against 0.25484 for ONNX, median absolute difference 0.0 trips, p99 0.043. A few rows differ by more than 2 trips because a rounded feature lands on the other side of a split threshold, so the tests assert aggregate and 99th-percentile bounds, not elementwise equality.

I ran the gateway against the real service, killed the service and recorded what came back. With the model up, gateway answers matched direct model answers exactly. With it killed, all 40 requests came from the fallback: 10 as model errors before the breaker opened, 30 with the breaker open. After restart and the 10-second open interval, 20 of 20 came from the model again.

The fallback is one stored number per zone, the same slot a week before the snapshot's next target, and the gateway returns it unchanged until the file is regenerated. During a long outage it drifts away from the right time of day. On synthetic load from a 2 vCPU container, the forecast service answers one request at a time at p50 2.4 ms and p99 about 6 ms. I didn't measure the gateway under load.

The control run with nothing injected also alerts, at 42 hours, so I can't cleanly say how fast it detects the real shifts. It misses a one-hour clock shift by 0.002 PSI. On clean April to June data it false-alarms on 36 of 1,776 hourly checks, on 8 distinct days, 4 of them weekend days. On the real March 2020 collapse it alerted about three days after trips fell below 80% of normal. It belongs on a dashboard, not a pager.

Mistakes along the way

  • My first drift monitor compared raw counts to a reference period and false-alarmed constantly, because a window that happened to contain Midtown zones looks different from one that doesn't, whatever the demand is. I normalised each value by the zone's expected count for that weekday and hour and computed PSI within tiers of that expectation. The false alarms dropped. They didn't go away.
  • My first ablation silently did nothing, because the column-dropping setting I passed to LightGBM has no effect on in-memory arrays. The script now slices the columns and asserts the feature names.
  • An ADR of mine claimed the ONNX parity bounds were asserted in tests when they weren't. I corrected the ADR and added the assertions.

Limits

  • One horizon and one month of test data. Other horizons, seasons and holidays are untested.
  • The same three June weeks scored the model, the baselines, the ablation, the hierarchy and the sparse-zone rule. Nothing was held back from all of them, so the headline is a backtest score and there's no untouched final test.
  • No uncertainty on most comparisons: three folds, and seed spread measured only for the full model.
  • The service forecasts from a snapshot loaded at startup. There's no ingestion path.
  • The service reports 258 zones where the backtest scores 262, and I didn't trace which four or why.
  • The gateway ran from the test classpath because a Maven plugin couldn't be downloaded in my container, so the packaged jar has never been run.

What I'd do next: a shrinkage model for low-count zones instead of a routing rule, more horizons and a holiday period, a drift threshold recalibrated on a rolling clean window with weekends modelled separately, and a gateway fallback computed per request.

Run it yourself

pip install -e '.[dev]'
ruff check . && pytest -q                  # 33 tests on synthetic data
mvn -B -f gateway/pom.xml test             # 6 gateway tests

scripts/fetch_tlc.sh data/raw              # six 2023 files and the zone lookup, about 320 MB
scripts/serve_local.sh data/raw            # trains, writes the snapshot, serves on :8000
python scripts/run_backtest.py data/raw 2023 1 6 --horizon 4   # the table above, about 5 minutes

Every other table has its own script, with the exact command in its docstring. Training and export take a few minutes on 2 vCPU.
