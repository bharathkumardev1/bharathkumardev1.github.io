Finding the page that answers a question about a 10-K

When an analyst asks about a filing, the answer can only be as good as the pages retrieval puts in front of the model. FinanceBench labels the page that answers each of its questions, so I could measure retrieval on its own, one step at a time, on questions I never tuned on.

Benchmark
FinanceBench: 150 analyst questions over 360 SEC filings, 53,399 pages
Held out
100 questions kept out of all tuning, which used the other 50
Result
Hit@10 from 0.14 to 0.75 on the held-out questions
Serving
BM25 on one core: 126 queries a second at 12 ms p95

It holds the 84 filings that FinanceBench questions cite, from 32 companies, out of the benchmark's 360. The first search fetches 114 KB of index data, then about 170 KB of compressed page text for each filing it opens. The tests run it against the Python pipeline on every benchmark question it can search (146 of 150, 438 question and setting pairs): same top 10 pages in the same order, same scores to the last bit.

How it narrows the search

Filings share most of their vocabulary: every 10-K has a balance sheet, a risk section and the same accounting terms. BM25 over all 53,399 pages puts a page from the right filing in its top 10 for only 42% of the held-out questions, so the first step isn't ranking. The filter reads the company, fiscal year and quarter from the question and keeps the matching filings, 2.5 of 360 on average. BM25 then ranks only their pages, and questions about a financial statement get that statement's pages first.

What each step is worth

I split the questions once: 50 for development and 100 held out. Everything I tuned, I tuned on the 50, and everything below is the 100. Hit@10 asks whether the labeled page made the top 10, which is what a model answering from ten retrieved pages needs.

The filter recognized the company in 97 of the 100 held-out questions and kept the filing with the answer for 96. On its own it took Hit@10 from 0.14 to 0.43 (+0.29, 95% interval +0.20 to +0.38).

Routing is worth as much again, and it's a small piece of domain knowledge. For 78 of the 150 questions the labeled page is a balance sheet, income statement or cash flow statement: a table of numbers that shares almost no words with "what is the FY2019 fixed asset turnover ratio". Questions that name a statement, or a line item or ratio that lives on one, get those pages first. 62 of the 100 held-out questions trigger it, and Hit@10 went from 0.43 to 0.71 (+0.28, 95% interval +0.19 to +0.37).

Leaving the company's name out of the query is the step I'm least sure of. Without routing it hurts (0.43 to 0.33), because the name is one of the few words a statement page shares with the question. With routing it adds +0.04, 95% interval -0.02 to +0.10, which is within noise.

The embedding model didn't earn its cost. Fused with BM25, MiniLM scored 0.73 against BM25's 0.75 on the held-out questions (-0.02, 95% interval -0.08 to +0.03) and takes 13 ms a query instead of 2.4. On the 50 development questions it looked better (0.78 against 0.66), which is why it's the configuration I committed to before testing; a gap that size on 50 questions turned out to be noise. Without the filter MiniLM does beat BM25 (0.24 against 0.14), because it finds the right filing more often (61% against 42%). The filter makes that redundant.

25 of the held-out questions need more than one page. The BM25 pipeline gets 66% of their labeled pages into the top 10, and the hybrid 64%.

Where it still misses

Every held-out question whose answer page missed the top 10 goes in the first stage of the pipeline that lost it. The rules run on every evaluation, so the counts change when the code does. These are the hybrid pipeline's misses, the configuration I committed to before testing.

The biggest group, narrative pages that share almost no words with the question, is the case a cross-encoder reranker is meant for. Routing's own failures are few: 2 questions needed a statement page without saying so, and 1 routed to the right kind of statement but ranked a different statement page first.

As a service

Behind the FastAPI service, with one worker pinned to one CPU core and the load generator on the other, BM25 serves 126 requests a second to a single client (p50 7.6 ms, p95 12 ms) and up to 162 as clients are added; the hybrid tops out at 55. No request failed at any load.

Pricing one vCPU at half an AWS c7i.large's on-demand rate, that's $0.10 per million BM25 queries and $0.25 for the hybrid, if this throughput carries over to that vCPU, which I haven't measured.

Two smaller checks

Adding filings without a rebuild

The BM25 index is kept in segments so filings can be added without rebuilding it. With 36 filings held out and added back in batches, every score on 300 queries matched a one-pass build exactly, and so did every top 100. A full build takes 13.1 s; each batch took 0.42 to 0.64 s.

Chunk size

Chunking pages into smaller passages didn't help. 650-token chunks score the same as whole pages (0.75), and 256- and 128-token chunks score 0.71 and 0.72 while indexing two to four times as many units, so the index stays at one entry per page.

Run it yourself

The repo downloads FinanceBench at a pinned commit and checks every PDF against its SHA-256, so a rerun scores the same pages:

make install
make data      # 150 questions, 360 PDFs (about 670 MB), page text
make embed     # MiniLM over every page: hours on a laptop CPU, resumable
make eval      # every configuration on dev and test, and RESULTS.md
make studies   # the incremental-index check and the chunk-size study
make loadtest

On every push, CI runs the tests on Python 3.11 and 3.13, a regression gate that runs the BM25 pipeline over the 40 filings behind the dev questions and fails if Hit@10 drops more than one question, a smoke test of the Docker image, a secret scan, and the browser port's parity test against the Python scores.

Retrieval numbers on this page are from the code at commit 8034887, run on 2026-10-21. Every results file, with the command and commit that wrote it, is in RESULTS.md.
