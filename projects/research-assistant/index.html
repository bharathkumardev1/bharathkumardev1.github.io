A research assistant that reviews its own answers

It answers questions about research papers and cites its passages. A second model call reviews each answer and, when something is missing, writes a new search query and goes around again. Every round costs calls and seconds, so the question is whether the review earns them.

How a question is answered

  1. Retrieve. MiniLM embeddings through ONNX Runtime, with the weights checked by SHA-256, and an exact cosine search for the top 5 passages. A paper is a few hundred passages, so exact search costs milliseconds and an approximate index would only cost recall.
  2. Answer. The model sees the passages numbered [1] to [5] and replies in a JSON schema: a short answer, the passages that support it, and a flag for "the passages don't answer this". Made-up passage numbers are dropped.
  3. Review. A second call reads the question, the answer and the full text of what it cites, marks each part supported or not, and if something is missing writes one search query to find it.
  4. Again. New passages are merged with the old ones and the answer is redone from all of them.

Model calls go through one small interface, LLMClient, with retries in my code rather than the SDK, so every retry shows up in the trace and the tests can count them.

How a run ends

One of five ways, and the result says which. The deadline and the budget are checked before every call.

StatusWhen
answeredThe review accepted the answer, or found it lacking with no query to try. A single pass always ends here.
round capThree rounds done.
no new passagesThe refined query found only passages the last answer already had.
deadline120 seconds passed.
budgetThe next call could take spending past the cap.

How it's measured

In QASPER (Dasigi et al., NAACL 2021), annotators answered each question after reading the whole paper and marked the paragraphs their answer rests on, so a system is scored on what it cites as well as what it says.

  • Each question is asked against its own paper, split into the dataset's paragraphs, so a citation matches the annotators' evidence exactly.
  • 150 dev questions for reading errors; 150 test questions, run once after the last change.
  • Same retrieval and models for both systems: gpt-6-luna answers and reviews, gpt-6.1-sol judges. The loop's first round replays the single pass's request, so any difference comes from the review.
  • Official answer and evidence F1, ported from allenai/qasper-led-baseline, plus judged accuracy. The judge is checked against 40 labels, which are an AI-assisted draft and not independent human annotation; an independent grade is pending.
  • Paired differences with 95% bootstrap intervals, the first failed stage for every wrong answer, and a $25 cap that refuses any call that could cross it.

Both runs used seed 0 at commit daac2a1 on 2026-10-28, and the whole recording cost $0.39 of a $5 cap. make check-replay reproduces every row with no key.

Paired by question, the 95% interval on the answer F1 difference is -0.011 to +0.037 on dev and -0.015 to +0.029 on test. On test, evidence F1 is +0.024 (-0.003 to +0.051) and judged accuracy is +2.7 points (0.000 to +0.060), which is 5 questions the loop got right and the single pass got wrong against 1 the other way. With six comparisons I don't read any of that as a finding.

The loop made 2.5 calls per question against 1. Answering cost about three times as much per question ($0.00028 against $0.00009 on test), the slowest 5% of questions took about 11 seconds against 2 to 3, and with judging included the bill differs by about 20%, because the judge is most of the spend. On this sample I can't say the loop is worth its extra calls.

The judge agreed with 35 of the 40 labels (87.5%, Cohen's kappa 0.74). Those labels are an AI-assisted draft, not independent human annotation, so this is not a human-versus-judge result. They cover 36 distinct questions, and several apply a stricter standard than the judge's rubric.

Rerunning without a key

Every model reply is recorded under a hash of its request, and every search goes to a run log with its scores. research-assistant check-replay reruns the evaluation from those files with no API key and lists any answer, citation or score that changes, so changing a prompt or the chunking fails the replay.

MiniLM runs in float32, so on another CPU a similarity can move in the sixth decimal and swap two near-tied paragraphs. A replay keeps the logged ranking when every score agrees to 1e-4 and fails when retrieval really changed. A reply the API cut off is billed, recorded as incomplete and never replayed as an answer.

Limits

  • QASPER papers are all NLP, and each question searches only its own paper.
  • Figures and tables aren't indexed.
  • With 150 test questions the interval on judged accuracy is 8 points either side, so small differences will show up as ties, and they did.
  • The judge is a model. The 40 labels that check it are an AI-assisted draft and say little about how far to trust it.
  • One seed, one sample of 150 questions per split, one model pair and one embedding model.

Run it yourself

make install   # the hashed lock, then the package and the test tools
make demo      # three sample papers, offline stub model, no key

research-assistant ingest path/to/papers/
research-assistant research "Which datasets do these papers evaluate on?"
research-assistant research "..." --max-rounds 1    # single pass

make qasper         # dev and test sets, with the release tarballs' SHA-256 recorded
make eval-dev       # 150 dev questions through both systems
make eval-test      # 150 test questions, once
make check-replay

The sample papers are short synthetic ones I wrote so the demo runs offline. The HTTP API adds key auth, per-caller rate limits and Prometheus metrics, and the Docker image is pinned by digest.
