A research assistant that reviews its own answers

It answers questions about research papers and cites the passages it used. A second model call reviews each answer against those passages, and when something is missing it writes a new search query and the loop goes around again. Every extra round costs calls and seconds, so what I want to know is whether the review earns them.

How a question is answered

  1. Retrieve. The query is embedded with all-MiniLM-L6-v2 through ONNX Runtime, with the weights checked against their SHA-256, and the top 5 passages come from an exact cosine search over a numpy matrix. A paper is a few hundred passages, so exact search takes milliseconds and an approximate index would only cost recall.
  2. Answer. The passages go to the model numbered [1] to [5], and the reply has to match a JSON schema: a short answer, the numbers of the passages that support it, and a flag for "the passages don't answer this". Passage numbers the model makes up are dropped.
  3. Review. A second call gets the question, the answer and the full text of the passages it cites, or of every passage it had when it declined. It says whether each part of the answer is supported and whether it answers the question, and if not, names what's missing and writes one search query to find it.
  4. Again. That query retrieves, new passages are merged with the ones already found, and the answer is redone from all of them.

Model calls go through one small interface, LLMClient. OpenAI's Responses API is the default, and another provider is one more class with a complete method. Retries on timeouts, rate limits and 5xx responses happen in my code rather than inside the SDK, so each retry shows up in the trace and the tests can count them.

How a run ends

Every run ends one of five ways, and the result says which. The deadline and the budget are checked before every model call, not after, so a run never starts a call it can't afford.

StatusWhen
answeredThe review accepted the answer, or found it lacking without a query to try. It's also how a single pass ends.
round capThree rounds done.
no new passagesThe refined query found only passages the last answer already had, so answering again would repeat it.
deadline120 seconds passed.
budgetThe next call could take spending past the cap.

How it's measured

In QASPER (Dasigi et al., NAACL 2021), annotators answered each question after reading the whole paper and marked the paragraphs their answer rests on. So a system is scored on what it cites as well as what it says, and the questions that can't be answered from the paper test whether it declines instead of guessing.

  • Each question is asked against its own paper, split into the dataset's own paragraphs, so a cited paragraph matches the annotators' evidence character for character.
  • 150 questions are drawn with seed 0 from the dev split and 150 from the test split. Dev is for reading errors and changing things. Test runs once, after the last change.
  • Both systems use the same retrieval and models: gpt-6-luna answers and reviews, and gpt-6.1-sol grades. The loop's first round sends exactly the single pass's request, so its first answer is the single pass's answer, replayed rather than paid for twice, and any difference comes from the review rounds.
  • Answer F1 and evidence F1 are the official metrics, ported from allenai/qasper-led-baseline. Evidence counts text paragraphs only, since this system can't retrieve a figure or a table.
  • Token F1 scores a right answer low when it's worded differently from every annotator, so a judge model also grades each answer against the annotators' answers. I grade 40 of the judged test answers myself without seeing its verdicts, and the results report how often we agree and Cohen's kappa.
  • Differences are paired by question, with 95% intervals from 10,000 bootstrap resamples. Each wrong answer gets the first stage that failed: evidence not retrieved, retrieved but not cited, cited but answered wrong, declined an answerable question, or answered an unanswerable one.
  • Spending is capped at $25 across everything recorded. Before each call the client prices the worst case, counting the prompt at a deliberately high one token per three characters plus the full output allowance, and refuses a call that could cross the cap.

When the test run is committed, this section gets the comparison: answer and evidence F1, judged accuracy, the judge's agreement with my grades, and dollars and seconds per question for both systems.

Rerunning without a key

Every model reply is recorded under a hash of its request, and every search, with its scores, and how each run stopped go to a run log. research-assistant check-replay reruns the evaluation from those two files with no API key and lists every answer, citation or score that comes out different. CI does this on every push once a recording is committed.

The search log is there because MiniLM runs in float32. On another CPU a similarity can move in the sixth decimal place, which is enough to swap two nearly tied paragraphs, change the prompt and miss the recorded reply. A replay recomputes each search and keeps the logged ranking when every score agrees to within 1e-4. A bigger difference means retrieval itself changed, and the replay fails instead of answering from different passages.

The replay doubles as a regression test: change a prompt, the top-k or the chunking and it fails, because the model would be asked something it wasn't. A reply the API cut off at its token limit is billed and recorded as incomplete, and never replayed as an answer.

Limits

  • QASPER papers are all NLP, and the evaluation searches each question's own paper. With many papers in one index, retrieval has more ways to go wrong than this measures.
  • Figures and tables aren't indexed, so questions whose evidence is a table are harder and are scored on text evidence only.
  • With 150 test questions, the 95% interval on judged accuracy is 7 to 8 points either side, so a small difference between the systems will show up as a tie.
  • The judge is a model. Forty hand-graded answers say how far to trust it, not that it's right on the rest.

Run it yourself

make install   # the hashed lock, then the package and the test tools
make demo      # three sample papers, offline stub model, no key

research-assistant ingest path/to/papers/
research-assistant research "Which datasets do these papers evaluate on?"
research-assistant research "..." --max-rounds 1    # single pass

make qasper         # dev and test sets, with the release tarballs' SHA-256 recorded
make eval-dev       # 150 dev questions through both systems
make eval-test      # 150 test questions, once
make labels         # 40 judged answers to grade by hand
make agreement      # the judge against those grades
make check-replay

The three sample papers are short synthetic ones I wrote so the demo runs offline; their answers say nothing about real research. The API serves the same loop over HTTP with key auth, per-caller rate limits and Prometheus metrics, and the Docker image is pinned by digest and installs from a hashed lock.
