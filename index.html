A retrieval and agent platform for credit analysis over 3M+ documents

Credit analysts work through filings and prior memos, and much of that work is repetitive multi-step reasoning. I designed the retrieval and agent orchestration layers of a LangGraph RAG platform that handles those intermediate steps first, so analysts review the output and keep the final decision.

  1. IngestPySpark on S3, incremental updates instead of rebuilds
  2. IndexSemantic chunking, metadata enrichment, OpenAI embeddings, FAISS
  3. RetrieveMetadata filtering, reranking, semantic caching
  4. ReasonLangGraph agents for analysis, validation, and delegation on GPT-4o
  5. ReviewAnalyst approval on sensitive decisions

Evaluation loop: a 500+ query benchmark scores retrieval (Hit Rate, MRR, recall) separately from generation (RAGAS), and every retrieval change is tested against it.

  • Score retrieval and generation separately. When an answer failed, separate scores showed whether retrieval, context construction, or the model caused it. That made tuning chunk size, overlap, top-k, embeddings, and reranking a set of measured experiments.
  • Update the index incrementally. Rebuilding an index of tens of millions of chunks for every change wasn't practical. New and changed documents flow through chunking, metadata enrichment, and embedding into incremental index updates, and source-level metadata traces each update back to its document. The corpus stays current without interrupting retrieval.
  • Optimize the workflow analysts actually wait on. The 10–20 second figure covers the full LangGraph run. Faster vector search alone would not have changed the analyst's experience, so I measured and tuned the whole path.
  • Choose models by task. I evaluated quantization and LoRA/QLoRA on open-source models for quality, latency, GPU memory, and cost. Infrastructure savings alone did not justify moving complex credit reasoning off the strongest model. Smaller models fit narrower, more deterministic tasks.
  • Keep the analyst in control. Agents take the repetitive intermediate steps, and human review stays on sensitive decisions, set up with risk and compliance teams. I also shipped the FastAPI layer that serves the platform to analyst dashboards.

Readmission risk tuned to how many patients a team can reach

Care-management teams can contact only so many patients. The goal was to find more patients who would benefit from early intervention while keeping the outreach workload manageable, so I tuned the models for that operating point.

  • Tune for the operating point. Threshold tuning on precision-recall trade-offs, with class weighting and resampling for heavy class imbalance, set the models to the team's capacity. Raw accuracy was never the target.
  • Validate the way the model runs. Time-based splits kept future information out of training to prevent temporal leakage.
  • Keep features that hold up. I engineered 150+ candidate features from labs, demographics, encounter history, and clinical notes, and kept about 100 for production based on predictive value and stability.
  • Explain every score. SHAP explanations showed clinical reviewers the drivers behind each patient's risk, and those explanations guided care-management prioritization for thousands of high-risk patients each month.
  • Run it like production software. MLflow and Airflow handled training, batch inference, registration, and retraining. Models shipped to SageMaker and EKS through CI/CD, and PSI drift monitoring triggered retraining reviews.

Demand forecasts measured where inventory is decided

Inventory planning happens per product and per store, so a single aggregate accuracy number can hide the forecasts that matter. I built and evaluated forecasting at that level, and separately built the customer segments behind targeted campaigns.

  • Evaluate at the decision level. Time-series and gradient-boosted models were scored with MAPE and RMSE across SKU and store level demand, which raised forecast accuracy about 14 percentage points over the prior baseline.
  • Build the data path first. PySpark, SQL, and BigQuery pipelines over 50M+ transactions surfaced seasonality and demand shifts before any modeling.
  • Segment for action. Clustering and cohort analysis produced customer segments for targeted campaigns, which lifted response rates about 12%.
  • Put results where teams decide. Tableau and Plotly dashboards gave merchandising, marketing, and supply-chain teams the forecasts and segments.

Answers questions about research papers, with a citation on every claim

Putting a folder of papers into one prompt hallucinates and loses track of which claim came from which paper. This project splits the work across three agents that share one FAISS index, and the evaluator's verdict decides whether the system is done or goes back for more evidence.

  1. RetrieveTop-k chunks from FAISS, merged across loops
  2. DraftAnswer from those chunks only, each claim tagged [n], validated with Pydantic
  3. CheckA second model call grades grounding and coverage

Loop: if the answer is thin, the evaluator writes a sharper query and the graph runs again, capped at 3 iterations and a per-run ceiling on API calls so it always stops and never runs up a bill.

  • Hardened like a public service. The FastAPI endpoint has per-caller rate limiting, request timeouts, scoped API keys, sanitized errors with a reference id, and Prometheus metrics. It ships as a Docker image deployed on Render.
  • Runs with no API key. An offline mode swaps in a deterministic embedder and a stub model, so anyone can run the real retrieval, graph, citation numbering, and report rendering locally.
  • States its limits. The bundled sample papers are synthetic, and the README says so. It is a tested single-instance service, not a multi-tenant system.
